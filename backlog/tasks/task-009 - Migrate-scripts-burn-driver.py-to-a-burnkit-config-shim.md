## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The overnight burn driver existed as a copy-adapted script in three repos (llmao -> here -> azure-dreams-remake), with fixes flowing forward only and no backport path. This repo was the middle generation, so it accumulated the cost: fixes made downstream never came back.

Two of those unbackported fixes were live bugs here:

1. **Unscoped process kills.** `kill_task_processes` and `cmd_kill` ran `pkill -9 -f "hermes chat"` and `pkill -9 -x` over `zelda3`/`sway`/`wtype`, machine-wide. This already killed an unrelated manual session. `HERMES_CMD` never wrote a pidfile, so there was nothing to scope a kill to, and line 297 passed a raw pid where `killpg` expects a pgid -- the fix is a coordinated three-part change.
2. **`prompt_header.txt` read REPO-relative**, so the prompt could only be composed from a checkout that happened to have the file at that path.

The shared mechanics now live in a separate library, `burnkit` (~/git/burnkit): the Backlog.md task queue, per-task git worktree lifecycle, launch backends, finish-marker protocol, and proof-of-done gates. This task reduces `scripts/burn/driver.py` to this repo's configuration of it -- a `BurnConfig` literal plus the project-specific callables -- keeping the same path, the same executable PEP 723 shape, and the same `./scripts/burn/driver.py {run,resume,status,kill}` commands so every doc reference stays valid.

`benchmark.py` stays here (it is strongly zelda3-specific) but switches from reaching into `driver.*` for shared helpers to importing them from `burnkit` directly, keeping only this repo's configured values (`MACHINE_GATES`, `REPO`, `BURN`, `TASKS_DIR`) as driver reads.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
driver.py 548 -> 171 lines; prompt_header.txt 28 -> 14; new test_driver.py at 184 lines / 19 tests.

The kill fix landed as all three parts, verified separately: burnkit's launched shell writes `$$` to `BURN_PIDFILE`, `burnkit.proc` terminates via `os.killpg(os.getpgid(pid), SIGKILL)`, and no `pkill` call survives under `scripts/burn/`. `benchmark.py` had an independent second copy of the regression -- its own `cmd_kill`, plus an `AB_HERMES_CMD` that wrote no pidfile at all -- which the plan had not accounted for; both are fixed rather than special-cased. Its pidfiles live under its own results dir rather than sharing `BURN/pids`, so `benchmark.py kill` cannot take down a live overnight run.

`test_driver.py::KillScopeTests` asserts the rule against the AST rather than the raw file text, so the scripts can keep documenting the machine-wide kill they used to run (that history is the whole reason burnkit exists) while still failing if one of them ever calls it again. Comments are absent from the AST, so they are excluded for free; docstrings are excluded explicitly.

One leaky seam surfaced and was fixed in burnkit rather than worked around here: `run_machine_gates` let `subprocess.TimeoutExpired` escape, so a single hung gate would end the whole overnight run instead of failing its own task. Gates now run in their own process group (`start_new_session=True`) and a timeout is returned as a failed gate with exit code 124, killing the group so a gate's spawned helpers (here: headless sway/zelda3/wtype) cannot survive to interfere with the next gate. Failing tests first (test_gates.py::test_a_timed_out_gate_fails_instead_of_ending_the_run, ::test_a_timed_out_gate_takes_its_whole_process_tree_with_it).

Two behavior changes worth naming:

- burnkit's `verify` adds an acceptance-criteria gate this driver never had: a task whose AC checklist still has unchecked items fails even with a DONE marker. The pre-migration prompt already instructed the agent to run `backlog task edit --check-ac`, so the gate is satisfiable, but a run that skipped it used to pass and now will not.
- An attempt's commits land on a per-task branch that is fast-forwarded into the burn branch on success, so the driver no longer requires this repo's own checkout to have `feat/zig-port-burn` out.

The scope gate is registered as `ANY_PATH` for both `code_change_prefixes` and `code_task_allowed_prefixes`, matching pre-migration behavior: every task is gated as a code task, and no path is out of scope. A port task can be a pure `build.zig` or unit-test-list edit and still change what the parity oracle sees, and no allow-list has ever been enforced here, so guessing one would block legitimate overnight work rather than catch anything. Narrowing it is worth a follow-up, not a blind guess during a migration.

burnkit is now public at <https://github.com/pythoninthegrass/burnkit> and tagged `v0.1.0`, so all three PEP 723 blocks (`driver.py`, `benchmark.py`, `test_driver.py`) pin `burnkit @ git+https://github.com/pythoninthegrass/burnkit@v0.1.0` instead of resolving the sibling checkout through `[tool.uv.sources]`. Verified against the tag, not the local path: `uv` fetched and built `v0.1.0` (e3cc7e6), `./scripts/burn/driver.py --help` and `./scripts/burn/benchmark.py --help` both work, and `./scripts/burn/test_driver.py` is 19/19.

`prek run --all-files` reformatted four unrelated `src/*.zig` files (pre-existing `zig fmt` drift on master); those were reverted to keep this commit scoped, and the drift is still there to deal with separately.

Doc sync (AC#9). `AGENTS.md` gains an "Overnight burn driver" section: driver.py is a config shim, burnkit owns the queue/worktree lifecycle/backends/marker protocol/gates, and what stays here is the models, the seven Zig gates, the local-only `feat/zig-port-burn`, the pre-port ROM, and the prompt prose. It also records the rule the shim shape makes load-bearing -- fix shared behavior in burnkit, not here (with the `pkill` history as the reason) -- and that the prompt's TASK STATUS/GIT/BAIL/FINISH sections are generated by burnkit and must not be re-added to `prompt_header.txt`.

`docs/bakeoff.md` said `driver.GATES` inside its machine-written `<!-- AB:BEGIN -->` block. The generator (`benchmark.py`) was already switched to `MACHINE_GATES` with the import change; this brings the stale committed artifact in line rather than waiting for the next A/B run to rewrite it.

`backlog/docs/doc-001` carried two line pointers into the old driver (`driver.py:404` for prompt composition, `driver.py:302-310` for the gate list). Both now name what actually composes/holds them (`burnkit.prompt`, `driver.py`'s `MACHINE_GATES`), with the pre-extraction line number kept as history rather than dropped.
